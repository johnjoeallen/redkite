# Bugs Fixed

A curated reference of real bugs found and fixed across RedKite's history, mined from the git log. This isn't every "fix"-labeled commit — pure renames, copy changes, and refactors with no behavior change are left out — just ones with a genuine symptom, root cause, and fix worth recording. See [Evolution](evolution.md) for the fuller narrative of how the project got here; this page is the debugging log version of the same history.

## Dependency Resolution & Version Detection

- **Conflict-losing versions parsed as real components** (`a3b7e37`) — `mvn dependency:tree` marks a version that lost Maven's "nearest wins" conflict resolution as `(omitted for conflict with X)`; these lines were being read as real components, sometimes locking a dependency at the losing version. Fixed by skipping any line containing `(omitted`, and preferring the tree's resolved version over a POM-declared one when they disagree.
- **Aggregator POM version contamination** (`155f60c`) — `dependency:tree` on a multi-module root POM prints aggregated output for every child module; the scanner was attributing all of it to the root POM, producing components at the wrong version. Fixed by skipping the tree run entirely for aggregator POMs — each leaf module already gets its own correct run.
- **`<parent>` version corrupted into an unresolvable property** (`1b62694`) — when a parent POM itself had an upgrade recommendation, its literal `<parent>` version was normalized into a `${...}` property reference — but Maven resolves `<parent>` before `<properties>`, so the reference could never interpolate. Parent versions now always stay literal.
- **A pinned parent could write its own version property back onto itself** (`df88bfa`) — when an external parent's version came from an inherited/CI-injected property this POM doesn't define, the unresolved `${propertyName}` text was fed back in as the upgrade target, producing `<revision>${revision}</revision>`.
- **Property-backed dependency-management pins surfaced raw** (`66243fc`) — a `<version>${propName}</version>` entry was read verbatim rather than resolved, so the unresolved reference flowed through as the "recommended" version and could be written back as `<logback.version>${logback.version}</logback.version>`, wiping out the real value.
- **BOM imports misclassified as plain version pins** (`8199398`) — the scanner never read `<type>` on a `dependencyManagement` entry, so a genuine BOM import (Spring Cloud, an AWS SDK BOM) was indistinguishable from an ordinary managed-version override.
- **Local `dependencyManagement` entries invisible outside aggregator modules** (`e32dea4`) — a leaf module's own overrides, including RedKite's own prior CVE-fix pins, weren't promoted to components at all on non-aggregator modules, making them indistinguishable from ordinary Maven mediation.
- **Managed version resolution didn't chase a property whose own value was another property** (`0fa7a3b`) — the real Jackson 2.22.1 BOM defines `jackson.version.core` as literally `${jackson.version}`; a single-level lookup would have used that unresolved string as the managed version. Fixed with a cycle-guarded property-chain resolver, alongside distinguishing a confirmed-absent artifact from a transport error when fetching a POM (previously collapsed into the same empty result, letting an unreachable optional mirror masquerade as "this artifact doesn't exist").
- **A newly-created property could shadow one a parent POM already owns** (`8839e9b`) — normalizing a dependency's literal version into a property always used `artifactId + ".version"` with no awareness of what the project's parent chain already uses that exact name for. A Spring Boot parent, for example, defines properties like `jackson-bom.version` to control its own internal BOM imports; a same-named local property silently redefines it for everything the parent manages through it — not just the dependency the new property was meant for — breaking dependency resolution for a completely unrelated artifact. RedKite now checks a candidate name against every property the parent chain and imported BOMs already declare (data `ManagedVersionResolver` already collected internally but previously discarded) and falls back to a `groupId`-qualified name when the plain one would collide.

## Vulnerability (CVE) Detection & Remediation

- **CVE bleed-over across versions** (`67f5363`) — vulnerability lookups were keyed by `groupId:artifactId` only, so a CVE confirmed on one version (e.g. Spring Boot 3.5.13) was also reported against a different, actually-clean version (3.5.15) in the same multi-module scan. Fixed by including the affected version in the key everywhere findings are matched.
- **GHSA-only advisories invisible** (`c3a00b3`) — the CVE indicator skipped any finding with an empty `cves` list, hiding advisories that only had a GitHub Security Advisory ID and no CVE alias.
- **Pre-release versions offered as upgrade targets** (`0931553`) — alphas, milestones, and release candidates weren't excluded from the candidate list, so RedKite could recommend an unstable version as "the" upgrade.
- **Three-tier CVE resolution shipped with several real sub-bugs** (`b50b68c`) — overlapping/redundant OSV ranges for the same branch were matched against only the first containing range, which could wrongly conclude a downgrade fixes a CVE that's actually unbounded; a separate literal-to-property normalization pass was silently converting RedKite's own pins into properties; renaming the pin marker comment broke recognition of pins written by older code, causing duplicate entries on every subsequent apply.
- **Fixable CVE not treated as a reason to move a transitive dependency** (`665f43b`) — the transitive-recommendation logic only trusted an existing pin or an active conflict, so a transitive dependency with a known, fixable CVE and nothing else forcing it fell through to "no upgrade recommended" — the CVE tab counted it as fixable, but there was nothing to actually apply.
- **CVE upgrades silently no-op'd on a component marked unmanaged** (`77a14b9`) — converting a bare "unmanaged" marker comment into a real pin only updated an accompanying `<dependency>` element if one existed — but an unmanaged marker never has one, so the comment claimed a pin at the new version while nothing on disk actually enforced it.
- **OSV queried once per candidate version during a CVE search** (`ccdb5f5`) — the three-tier search could probe ~16 candidate versions per vulnerable component, each its own network round-trip (3,115 calls observed on one real project's first scan). Switched to OSV's package-level query (every advisory for a package in one call) with local version-range matching, dropping the same scan to 344 calls.
- **A dependency's own vulnerable transitive children were invisible** (`a5819ed`, `4a2dc40`, `99ad2f5`) — a clean, non-vulnerable direct dependency gave no indication that something it pulled in transitively had a known CVE unless every card was expanded by hand. Added a severity-by-count rollup, deduplicated by exact component, with per-severity tooltips naming the specific child and advisory.

## Dependency Conflicts & Convergence (Maven Enforcer)

- **Enforcer conflict version parsing corrupted by tree annotations and trailing periods** (`d5beb84`, `b6cded6`) — Maven tree annotations like `2.21.2 (managed) <-- ...` reached the POM's `<version>` tag verbatim, and a trailing sentence period on a header-parsed version (`3.5.6.`) caused exact-match lookups to fail, producing false-positive conflicts.
- **Conflict version pre-selection discarded the originally-requested version** (`09d477d`) — the parser extracted the already-managed version instead of the version actually in conflict, so `conflictingVersions` was always empty and the dropdown pre-selected the version already pinned. A related bug in the same commit: unescaped `"` inside a double-quoted `onclick` attribute silently broke the Apply button.
- **Duplicate dependency-management entries when a project already managed the artifact** (`5a169b9`) — RedKite only checked for its *own* prior pin before inserting a new entry; a pre-existing project override for the same coordinate got a second, dead-weight entry alongside it instead of being taken over.
- **A second `<exclusions>` block on every exclusion fix** (`b3d6ea1`) — exclusions were inserted via line-based string splicing, and `applyExclusion` always inserted a fresh `<exclusions>` block even when one already existed — a genuine schema violation Maven's XSD rejects. Rewrote all POM mutation onto DOM parse/serialize.
- **Coordinated release-train families pinned inconsistently** (`296c51c`, `3a15d93`, `4b70f9f`) — a per-artifact conflict winner was computed in isolation, so a library whose modules must move together (Cucumber, Netty) could end up with incompatible sibling versions; fixed in three passes as the gap was found in the main auto-fix path, then in two separate fallback display paths that bypassed it entirely.
- **A computed conflict winner could override a project's deliberate version choice** (`a32092b`) — winner selection used `max()` over observed versions, which could cross a release line the project had deliberately avoided; also, Phase 2 verification stripped *all* dependency management (not just RedKite's own), simulating the deletion of every deliberate project pin and reporting real fixes as unresolvable.
- **The Jackson BOM bug: broadcasting one version across a family whose members are independently versioned** (`e616506` and the cluster around it) — the real Jackson 2.22.1 BOM manages `jackson-core`/`jackson-databind` at `2.22.1` but `jackson-annotations` at `2.22` (`2.22.1` is a genuine 404 on Maven Central); the existing family-alignment logic broadcast one literal target onto every member unconditionally, correct for a true release train but wrong for a BOM-governed family. Rewritten as `FamilyVersionAligner`, which reconciles each member against what its actual controlling BOM manages, never broadcasting a literal onto a member with its own resolvable version.
- **The multi-module "Auto-fix" button had no build validation or rollback** (`d5eddb6`) — it posted each pin individually to a single-pin endpoint with no pre/post-build check, so a pin that broke the build (e.g. an unresolvable convergence fix) stayed written permanently. Rewired onto the same validate → write → validate → revert-on-failure job every other apply path already used.
- **Selecting "No change" was ignored for a dependency with an active convergence conflict** (`a9c9e79`) — the client computed the applied version as `item.sel.value || data.resolvedVersion`; since an empty string is falsy in JavaScript, explicitly choosing "No change" always fell through to the computed resolved version, silently reapplying the fix regardless of what the user picked.

## Apply, Validation & Rollback

- **Validation-triggering SNAPSHOT components leaking across modules** (`c8fc792`) — a pre-pass builds the set of a project's own module coordinates so a module-to-module reference (like a test fixture's own wrapper modules) isn't mistaken for an external SNAPSHOT dependency; a related parsing bug stopped at the first matching XML node instead of iterating all of them, breaking key lookups whenever a child POM's `<parent>` block contained its own `<artifactId>` before the module's real one.
- **Startup validation process never fully killed, leaking a bound port** (`9205c23`) — `destroyForcibly()` on the `spring-boot:run` process only killed the `mvn` wrapper on Windows, leaving the forked JVM running and holding its port — the *next* validation run then failed with "port already in use," failing the apply and reverting a change that actually worked. Fixed by capturing and forcibly killing the whole descendant process tree, and running the startup check on a randomized free port so it can never collide with anything else.
- **Startup validation reported truncated logs and false failures** (`3710585`) — the reader thread stopped consuming output as soon as "Tomcat started on port" appeared, which fires before Spring finishes initializing (and never fires at all for non-servlet apps) — truncating the captured log and, for some apps, reporting a genuinely successful startup as failed once the timeout elapsed. Fixed to require the definitive "Started ... in ... seconds" banner.
- **Orphaned version properties left behind after a pin was replaced** (`b6400c8`) — a property normalized from a literal version could outlive the pin that created it, sitting as dead weight in every subsequent regeneration. Added a pass that drops unused `.version`-suffixed properties — carefully: a property a project's BOM references only internally (never appearing as a literal `${...}` in the child POM's own text) is protected by the scan's own provenance data, so it isn't wrongly deleted.
- **A version update for RedKite's own prior pin had nowhere to go** (`5f963b9`) — `patchPomXml` deliberately excludes RedKite's own pin elements from the normal patch path (to protect them from unrelated literal-to-property normalization), so picking a new version for an existing pin showed correctly in the apply preview but the generated POM came back identical to the original. Added a dedicated pass that updates a pin's own `<version>` and marker comment in place.
- **"Apply selected" silently did nothing when the patch set was empty** (`7e898e3`) — no feedback at all when a user's selections happened to produce no actual change. Replaced with a preview panel listing every pending change, or an honest "No changes."
- **Touching one dropdown discarded every other pending selection** (`a794e17`) — an earlier apply model required each change to be explicitly "accepted" one at a time; interacting with any single dropdown reset the rest. Changed the default to apply every visible recommended change, with an explicit Pin control as the way to exclude one.
- **A silent gate skipped a user's explicit version change** (`fa6c755`) — a `data-chosen` flag meant to prevent accidentally applying a server-side pre-selected default also silently excluded any dropdown the user *had* changed but that hadn't tripped the right code path, so Apply could send the original recommendation instead of what was actually selected.
- **Clicking the upgrade chip reset the dropdown back to the recommendation** (`196fe69`) — the chip's `onclick` was rendered server-side with the recommended version baked in; after a user picked a different version from the dropdown, clicking the (still-visible) chip silently reverted the selection.

## Remediation Counts, Filters & UI Consistency

RedKite's remediation view has had a recurring class of bug: a summary count (a banner chip, a tab count, a filter chip) computed from a *different* rule than the list of cards it's supposed to describe, so the two disagree. This happened enough times, in enough different places, that it's worth calling out as a pattern rather than just a list of isolated fixes:

- **Severity chips inflated by per-module duplication, CVE/Clean tabs claiming the same card, wrong "actionable" definition for the CVE tab, a hardcoded zero count** (`912af43`) — four distinct bugs in the same panel, all traced back to the same dependency being counted once per module it appeared in rather than once overall.
- **A "N clean hidden" label counting cards hidden by an unrelated filter** (`ef652f3`) — the transitive-visibility toggle's hidden count was folded into a label that claimed to describe something else entirely.
- **Filter tab counts frozen at server-render time** (`6af26c8`) — button counts didn't update as other filters changed, so "CVE 7" stayed put even after most of those 7 were hidden by an unrelated toggle.
- **The "Update recommended" banner overcounting by more than 3x the actual Findings total** (`b2e178a`, `6a15aa5`, `f6825f2`) — a pinned dependency (a deliberate decision *not* to move) still counted toward "needs an update," and a transitive dependency with no concrete reason to move (no pin, no conflict, no CVE) was counted too, even though the version selector for it already correctly defaulted to "No change." On one real project this was 170 vs. an actual Findings total of 46.
- **The remediation banner and the Findings/Clean/All tabs disagreeing outright** (`3e3e5c1`, `05325d8`, `b8e8cc3`, `a2a52df`, `88b00a9`) — the most involved instance of this pattern: `isCardClean` suppressed transitive dependencies with a real, *unfixable* CVE as a side effect of a different suppression rule; a severity badge printed "✓ Clean" whenever severity was `NONE`, regardless of whether the component actually needed attention for a non-CVE reason; a "No upgrade available" chip was shown whenever RedKite wasn't offering to apply anything, even when a newer version genuinely existed; and a version selector could render for a transitive dependency with nothing real behind it, defaulting to "No change" with no actual target. Each was fixed and verified live against a real scan; the banner and tabs were finally reconciled to compute their counts from the same per-dependency source rather than two independently-evolved rules.

## License Scanning

- **A dual-licensed dependency counted toward every license it declared** (`c433b7e`) — the license breakdown panel counted a dependency once per declared license rather than once overall, inflating every bucket a dual-licensed dependency happened to touch. Fixed to count each dependency under exactly one bucket: its single license, or its most-permissive one.
- **A single-license dependency was never eligible for the "most permissive" star** (`134ace7`) — the permissiveness picker required at least two licenses to have anything to compare, so a dependency with only one (ranked) license never got the highlight even when it deserved it.
- **Selecting a license filter could show zero matches with no explanation** (`ba050ab`, `d1cdc49`) — the license panel's counts are global across every module, but the module filter defaulted to one specific module with no "All modules" option, so a license whose matches lived in a different module silently showed nothing; separately, the default "Findings" view (which hides clean dependencies) could hide a filter's matches the same way. Both filters now reset to "all" when a license chip is selected.

## Repository & Settings Resolution

- **`settings.xml` discovery used the server process's working directory, not the project's** (`8c774cd`) — repository and credential resolution was rooted at wherever RedKite's own process happened to be launched from, not the project actually being scanned.
- **A `mirrorOf=*` mirror was bypassed** (`b6809ed`) — profile repositories were still queried directly even when a mirror covered everything, causing RedKite to hit the real upstream repository (e.g. a vendor's public Maven repo) instead of the configured corporate mirror.
- **`${env.VAR}` credential placeholders sent literally** (`6529cb1`) — an unresolved environment-variable placeholder in `settings.xml` could be sent as a literal Basic-auth credential instead of being resolved or dropped, turning an otherwise-accessible anonymous resource into a 401.
- **The version-metadata cache didn't actually clear on "Rescan (clear cache)"** (`1dea2c8`) — two independent causes: an H2-specific `MERGE INTO ... KEY` write silently failed under H2's PostgreSQL compatibility mode, and the in-memory clear operated on a provider instance that could be replaced by project reconfiguration before the next scan ran.

## Database & Schema

- **A schema migration failed on fresh installs** (`a9d398d`) — an `ALTER TABLE` ran unconditionally before the corresponding `CREATE TABLE`, so a brand-new database (with nothing yet to alter) failed at startup.
- **Metadata-gated `ALTER`s silently skipped on some database states** (`db4137f`, `256a25e`) — guards checking `getMetaData().getTables()` before altering a table could return no rows and silently skip the alter, leaving columns missing depending on exactly which prior schema version a database happened to be at. Eventually replaced with one unconditional, idempotent reconciliation pass (`ff64094`): every table created `IF NOT EXISTS`, every column added `IF NOT EXISTS` — safe to run against any prior state.
- **H2/PostgreSQL syntax incompatibilities** (`85ce621`, `8e47ac5`, `30d30d1`) — `bigserial`/`timestamptz` aren't valid in H2's PostgreSQL compatibility mode; H2 doesn't support PostgreSQL's `ON CONFLICT DO UPDATE SET ... excluded.*` syntax either, for both a cache-write path and scan ingest — each replaced with H2-native syntax or application-level deduplication.
